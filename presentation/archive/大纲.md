21. 标题是：（1）自动生成修复操作。 **GIDCL [15]** 图示：结合表格关联、语言模型生成的清洗函数以及分类器反馈，让系统逐步改进实际清洗过程。
22. 标题是：（2）候选正确答案。**Baran [6]** 图示：利用单元格和行列上下文生成候选修复值，再根据人工修复示例学习排序。
23. 标题是：（2）候选正确答案。**DataVinci [12]** 图示：则针对复杂字符串，结合语义和格式知识进行修改。

25. **HoloClean [3]** 将约束、统计规律和参考知识结合到概率模型中，通过联合推断选择更合理的修复。
26. **Rock [14]** 则将模型判断与逻辑规则结合，通过结构化推理协调不同证据。

28. **OTClean [17]** 则针对条件独立要求，在数据分布层面进行调整。



29. **什么样的修复才真正值得信任？**：图示：

    系统修复了大量错误，数据看起来更加整齐了。

    但如果它把原本正确的订单也修改了呢？

    更危险的是，这些修改可能直接影响最终的销售报表。

30. 标题：（1）评估修改的正确性。**Minimum Change ≠ Best Cleaning [19]** 指出，修改最少不等于修复最好，还需要考虑单元格实际出错的可能性。

31. 标题：（1）评估修改的正确性。**bNDCRepair [18]** 进一步考虑：如果规则本身就不准确呢？因此，它同时考虑修改数据和调整约束范围。

32. 标题：（1）评估修改的正确性。对于时间序列，**SHoTClean [20]** 将必须遵守的变化边界与统计趋势结合起来，避免修复结果违背物理限制。

33. 标题：（2）如何决定修改呢。**Auto-Fill [13]** 比较不同推理方式并校准置信度，在证据不足时允许保留缺失值。

34. 标题：（2）如何决定修改呢。**ActiveClean [21]** 认为，既然最终目标是训练模型，就应该优先清理对模型训练影响更大的记录。

35. 标题：（2）如何决定修改呢。**SAGA [22]** 则关注整条清洗流程，利用下游验证表现来选择操作、顺序和参数。



36. 但随着研究的发展，**Data Preparation 的目标已经不再局限于 Data Cleaning，而是进一步要求系统根据用户的真实意图，将原始数据准备成能够直接使用的结果。**
37. 例如：老板希望计算“真实销售额”。系统不仅要修复错误，还需要理解取消订单是否计入、退款如何处理，以及最终应该生成什么样的结果。（想说明的是：引入preparation）图示：应该是老板的希望的演变
38. 图示：**CoWrangler [27]、MegaTran [28]** 这样的研究，已经开始探索用户交互、自然语言理解和自动化操作；
39. **PrepBench [30]** 则进一步关注需求澄清与正确执行等能力。
40. 展示：数据准备所面对的数据规模和复杂程度也在不断增加。
41. **企业数据工程研究 [23]** 反映了复杂数据环境和上下文不足带来的挑战
42. **Pneuma [24]** 尝试利用表结构、内容和描述等知识，帮助系统找到与任务相关的数据。
43. 数据准备的操作本身也越来越复杂。图示大意：一个任务可能需要连续完成数据筛选、结构转换、多表连接和聚合计算。即使每一步代码都能运行，错误的操作顺序或业务口径仍然可能导致最终结果不正确。
44. **Auto-Tables [25]** 研究表结构转换，**Auto-Prep [26]** 考虑转换与连接之间的依赖关系
45.  **DeepPrep [29]** 通过多路径探索与执行反馈改进复杂流程。





46. future：现在已经从预处理自动化到agent了

47. **第一，知识的持续积累与自进化。** Agent 能否把每次任务中发现的规则、语义和成功经验保存下来，经过验证后用于未来任务，而不是每次都从零开始？

    **第二，知识的可信更新。** 如果新知识与旧规则发生冲突，或者业务规则已经改变，系统能否识别、更新甚至撤销过时知识？

    **第三，主动知识获取。** 当系统无法确定某个操作时，能否主动判断应该检查数据、检索文档，还是向用户询问？

48. **第四，跨任务知识迁移。** 在数据清洗中发现的字段含义和表间关系，能否继续支持后续的连接、转换和分析任务？

    **第五，知识驱动的过程验证。** Agent 能否利用已有规则检查每一步的中间结果，及时发现错误，而不是等到最后才重新执行？
