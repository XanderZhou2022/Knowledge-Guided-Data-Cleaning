# Knowledge-Guided Data Cleaning: From Error Correction to Intelligent Data Preparation

**10 分钟 Survey Presentation 中文口头稿**

## 1. 开场：一个看似简单的数据分析任务｜0:00–0:40

假设今天你是一家电商平台的数据分析师。

老板给了你一个看起来非常简单的任务：

“帮我计算一下，去年每个月、每座城市的真实销售额。”

你可能觉得，只要找到订单表，按照月份和城市分组，再求和就好了。

但当你真正打开数据，问题出现了。

同一笔订单可能被记录两次；同一个城市可能有不同写法；有些邮编和城市对不上；甚至不同系统中的客户信息也不一致。

这时，真正困难的已经不是怎么计算，而是：

**我们怎么知道数据哪里错了？又应该根据什么来修改？**

这正是我们这篇 Survey 关注的核心问题：知识如何帮助系统检测和修复数据，并进一步支持整个数据准备过程。

## 2. 第一关：谁来告诉系统什么是正确的？｜0:40–1:45

首先，假设我们发现一条订单记录的邮编和城市不匹配。

计算机怎么知道这是一个错误？

最直接的办法，就是提前告诉它规则。

例如，**CFD [1]** 可以表达在特定业务条件下，邮编与城市应该满足怎样的对应关系。

当规则越来越多，**NADEEF [7]** 提供统一框架，让不同规则能够共同参与检测和修复。

但这里出现了第一个问题：

**发现两个字段相互矛盾，并不代表我们知道哪个字段是错的。**

到底是邮编错了，还是城市错了？

**Certain Fixes [2]** 提出，可以先确认客户编号这样的关键属性，再利用可信主数据推导其他字段的修改。

**KATARA [8]** 则进一步利用外部知识库，将数据表与真实世界的实体和关系对应起来，并通过人工核验处理不确定情况。

所以，早期研究的核心思路是：

**通过规则和可信的外部知识，为数据清洗提供明确依据。**

但是，如果一家企业有几百张表、数千个字段，我们不可能永远依靠人工维护所有规则。

于是，研究进入了第二个问题。

## 3. 第二关：没有人工规则，系统如何获得可信的清洗知识？｜1:45–3:25

那么，**系统能不能自己从数据中发现这些知识？**

**Parallel Rule Discovery [9]** 通过多轮采样和并行搜索，提高规则发现的效率。

而对于时间序列，**TSDDiscover [10]** 进一步考虑时间延迟和正常波动，学习更复杂的时间依赖关系。

除了直接搜索规则，我们也可以利用模型学习知识。

**Garf [4]** 利用生成模型学习字段之间的关联，并提炼成可用于修复的规则。

**Auto-Test [11]** 则从其他数据表学习不同语义类别的取值要求，再判断这些要求能否应用到当前数据。

但到这里，又出现了一个问题：

**如果原始数据本身就存在错误，我们怎么知道学出来的规律是可信的？**

例如，一座城市的名称在多数记录中都拼错了，仅仅依靠出现频率就可能形成错误判断。

因此，**Raha [5]** 综合多个检测器的信号，选择少量代表性记录让用户标注，再利用这些反馈识别类似错误。

所以，这一阶段的核心变化是：

**知识不再完全依赖人工预先定义，而是可以从数据中发现、从其他数据迁移，并通过人工反馈不断完善。**



## 4. 第三关：有了知识，怎样把它转化成具体修复？｜3:25–5:05

现在，系统已经学到了邮编和城市的关联，也获得了一些用户反馈。

但是，面对一条城市名称错误的订单，我们究竟应该执行什么修改？

**这就需要把已有知识转化成具体的修复决策。**

首先，系统可以尝试自动生成修复操作。

**GIDCL [15]** 结合表格关联、语言模型生成的清洗函数以及分类器反馈，让系统逐步改进实际清洗过程。

另一种思路，是先提出多个可能的答案，再选择最合理的一个。

**Baran [6]** 利用单元格和行列上下文生成候选修复值，再根据人工修复示例学习排序。

**DataVinci [12]** 则针对复杂字符串，结合语义和格式知识进行修改。

但如果不同知识来源支持不同答案呢？

例如，邮编支持城市 A，历史订单却更支持城市 B。

**HoloClean [3]** 将约束、统计规律和参考知识结合到概率模型中，通过联合推断选择更合理的修复。

**Rock [14]** 则将模型判断与逻辑规则结合，通过结构化推理协调不同证据。

而且，知识还会影响我们究竟修改什么。

例如，一行记录可能混合了两个客户的信息。

**Splitting Tuples [16]** 利用实体与属性知识，将混合记录拆分。

**OTClean [17]** 则针对条件独立要求，在数据分布层面进行调整。

所以，这一阶段真正解决的是：

**如何把规则、统计规律、外部事实和用户反馈等知识，转化为具体的数据修改。**

知识不仅决定选择哪个答案，也影响应该采用什么操作、修改哪个层次的数据。

但新的问题出现了：

**即使修改符合这些知识，我们又如何确定修改结果真的可靠？**

## 5. 第四关：改得越干净，就一定越好吗？｜5:05–6:45

想象一下，系统修复了大量错误，数据看起来更加整齐了。

但如果它把原本正确的订单也修改了呢？

更危险的是，这些修改可能直接影响最终的销售报表。

所以，研究开始重新思考：**什么样的修复才真正值得信任？**

**Minimum Change ≠ Best Cleaning [19]** 指出，修改最少不等于修复最好，还需要考虑单元格实际出错的可能性。

**bNDCRepair [18]** 进一步考虑：如果规则本身就不准确呢？因此，它同时考虑修改数据和调整约束范围。

对于时间序列，**SHoTClean [20]** 将必须遵守的变化边界与统计趋势结合起来，避免修复结果违背物理限制。

还有一个非常重要的选择：

**如果系统没有足够的证据，我们能不能干脆不修改？**

**Auto-Fill [13]** 比较不同推理方式并校准置信度，在证据不足时允许保留缺失值。

但是，即使每个值都修复正确了，老板的分析任务就一定能做得更好吗？

**ActiveClean [21]** 认为，既然最终目标是训练模型，就应该优先清理对模型训练影响更大的记录。

**SAGA [22]** 则关注整条清洗流程，利用下游验证表现来选择操作、顺序和参数。

这带来了一个重要结论：

**数据事实正确、满足规则，以及改善下游任务，其实是三个不同的目标。**

因此，评价清洗系统，不能只看修复了多少错误，还要考虑误改、任务收益和成本。

到这里，我们似乎完成了数据清洗。

但其实还忽略了一件更重要的事情。

## 6. 第五关：为什么 Data Preparation 同样离不开知识？｜6:45–8:55

前面我们讨论了知识如何帮助系统发现和修复数据错误。

但随着研究的发展，**Data Preparation 的目标已经不再局限于 Data Cleaning，而是进一步要求系统根据用户的真实意图，将原始数据准备成能够直接使用的结果。**

例如，老板希望计算“真实销售额”。系统不仅要修复错误，还需要理解取消订单是否计入、退款如何处理，以及最终应该生成什么样的结果。

这些问题往往存在歧义，而**业务背景、历史口径和用户偏好等知识，可以帮助系统理解需求，减少不必要的猜测。**

像 **CoWrangler [27]、MegaTran [28]** 这样的研究，已经开始探索用户交互、自然语言理解和自动化操作；**PrepBench [30]** 则进一步关注需求澄清与正确执行等能力。

**其次，数据准备所面对的数据规模和复杂程度也在不断增加。**

过去可能只需要处理几张表格，但在企业场景下，数据库可能包含成百上千张表，而且字段名称不清楚、表间关系复杂。

这时，系统首先需要知道数据在哪里、每张表和每一列代表什么，以及不同数据之间存在怎样的关联。

**企业数据工程研究 [23]** 反映了复杂数据环境和上下文不足带来的挑战，而 **Pneuma [24]** 尝试利用表结构、内容和描述等知识，帮助系统找到与任务相关的数据。

**第三，数据准备的操作本身也越来越复杂。**

一个任务可能需要连续完成数据筛选、结构转换、多表连接和聚合计算。即使每一步代码都能运行，错误的操作顺序或业务口径仍然可能导致最终结果不正确。

因此，系统不仅需要执行能力，还需要关于**如何选择合理操作、怎样安排处理步骤，以及如何验证中间结果**的知识。

例如，**Auto-Tables [25]** 研究表结构转换，**Auto-Prep [26]** 考虑转换与连接之间的依赖关系，而 **DeepPrep [29]** 通过多路径探索与执行反馈改进复杂流程。

这些研究展示了自动化数据准备的不同能力，也让我们看到进一步引入操作指南、历史经验和验证规则的价值。

所以，我们可以发现，**Knowledge 的作用并不止于 Data Cleaning。**

随着 Data Preparation 从修复数据走向理解用户需求、处理大规模复杂数据和完成多步骤任务，系统也越来越依赖三类知识：

**用户意图和业务背景知识、数据本身的语义与关联知识，以及操作流程和验证知识。**

那么，既然这些知识能够在整个数据准备过程中发挥作用，我们能否让 Agent 在每次任务中持续积累、验证和复用知识，从而逐渐形成自进化的数据准备系统？

这就是我们最后想讨论的未来方向。

## 7. Future Directions：走向能够持续学习的数据准备 Agent｜8:55–9:50

最后，我们认为，随着 Data Preparation Agent 的发展，知识还可能发挥更重要的作用。

这里有几个值得进一步探索的方向。

**第一，知识的持续积累与自进化。** Agent 能否把每次任务中发现的规则、语义和成功经验保存下来，经过验证后用于未来任务，而不是每次都从零开始？

**第二，知识的可信更新。** 如果新知识与旧规则发生冲突，或者业务规则已经改变，系统能否识别、更新甚至撤销过时知识？

**第三，主动知识获取。** 当系统无法确定某个操作时，能否主动判断应该检查数据、检索文档，还是向用户询问？

**第四，跨任务知识迁移。** 在数据清洗中发现的字段含义和表间关系，能否继续支持后续的连接、转换和分析任务？

**第五，知识驱动的过程验证。** Agent 能否利用已有规则检查每一步的中间结果，及时发现错误，而不是等到最后才重新执行？

同时，我们还需要从长期角度评价这些系统：知识积累究竟能否持续提高准确率，并减少人工反馈和计算成本？

回顾整篇 Survey，从人工定义知识，到自动学习、使用和验证知识，再到未来可能的持续积累和跨任务复用，我们看到了一条清晰的研究主线。

**Knowledge should not only help agents clean data, but also help them learn from data preparation itself.**
